# Waymark Mobile — Feature 05 Booking Security Specification
## Document: `FEATURE_05_BOOKING_SECURITY.md`
### Task: 05.1.3 — Reservation Database & Transaction Security Foundation

---

## 1. Feature 05.1 Security Scope & Posture

Waymark Mobile Feature 05 introduces ticketing, reservations, and payment foundations. The core security mandate for Feature 05 is:

> **Zero Client Trust in Booking Authority:** Mobile clients are strictly untrusted presentation environments. Mobile apps may browse public catalogs, request quotes, and initiate reservations, but they can **never** set authoritative prices, transition their own booking state to `confirmed` or `ticket_issued`, directly decrement departure inventory, or forge ownership of reservations.

---

## 2. Database Schema Overview

The database migration `supabase/migrations/20261126160000_waymark_booking_foundation.sql` provisions four relational entities:

1. **`public.bookable_departures`**: Catalog of verified operational transit departures (corridors, schedules, transit modes, operator IDs).
2. **`public.departure_inventory`**: Real-time capacity ledger tracking `total_capacity`, `allocated_capacity`, and `held_capacity`.
3. **`public.booking_reservations`**: Private traveler booking ledger linking users (`auth.users`), departures, integer minor-unit monetary totals, and lifecycle statuses.
4. **`public.booking_idempotency_records`**: Operation-level request fingerprinting table preventing duplicate charging and double-reservations.

---

## 3. Reservation Ownership & RLS Policy Matrix

All private tables have Row Level Security enabled (`ENABLE ROW LEVEL SECURITY`). Default access permissions are explicitly revoked from `public` and `anon`.

| Table | Role | Operation | RLS Policy Predicate | Security Purpose |
| :--- | :--- | :--- | :--- | :--- |
| `bookable_departures` | `anon`, `authenticated` | `SELECT` | `using (true)` | Public catalog lookup |
| `bookable_departures` | `anon`, `authenticated` | `INSERT/UPDATE/DELETE` | **DENIED** (No grant) | Prevents client tampering with schedules |
| `departure_inventory` | `anon`, `authenticated` | `SELECT` | `using (true)` | Public real-time capacity visibility |
| `departure_inventory` | `anon`, `authenticated` | `INSERT/UPDATE/DELETE` | **DENIED** (No grant) | Prevents client capacity tampering |
| `booking_reservations` | `anon` | `ALL` | **DENIED** (Revoked) | Protects traveler privacy |
| `booking_reservations` | `authenticated` | `SELECT` | `using (auth.uid() = user_id)` | Strict traveler isolation |
| `booking_reservations` | `authenticated` | `INSERT/UPDATE/DELETE` | **DENIED** (No grant) | Prevents direct status/price forgery |
| `booking_idempotency_records` | `authenticated` | `SELECT` | `using (auth.uid() = user_id)` | Idempotency result isolation |
| `booking_idempotency_records` | `authenticated` | `INSERT/UPDATE/DELETE` | **DENIED** (No grant) | Prevents idempotency manipulation |

---

## 4. Role and GRANT Restrictions

- **`anon` Role**:
  - `GRANT SELECT ON public.bookable_departures`
  - `GRANT SELECT ON public.departure_inventory`
  - Cannot access any private booking records or idempotency keys.
- **`authenticated` Role**:
  - Inherits public catalog access.
  - `GRANT SELECT ON public.booking_reservations` (governed by `auth.uid() = user_id`).
  - `GRANT SELECT ON public.booking_idempotency_records` (governed by `auth.uid() = user_id`).
  - Direct client `INSERT`, `UPDATE`, and `DELETE` privileges are explicitly withheld.
- **`service_role` (Trusted Backend / RPC)**:
  - Bypasses RLS strictly within authenticated server execution contexts (Edge Functions, backend jobs).
  - Credentials **never** packaged into mobile client bundles.

---

## 5. Operator Trust Boundary

- Operator identity (`operator_id`) must match verified transit authorities in the registry.
- Client requests cannot designate arbitrary operator codes.
- Departures with `inventory_source = 'sample_data'` are permanently quarantined from the booking engine and can never be transitioned into operational reservations.

---

## 6. Fare Trust Boundary & Monetary Modeling

- Authoritative pricing is governed by `FareQuote` objects generated by trusted quotation engines.
- Monetary amounts are modeled strictly in **positive integer minor units** (`total_amount_minor_units bigint check (total_amount_minor_units >= 0)`).
- Floating-point numbers are prohibited in database storage and application validation.
- Currency is constrained to recognized ISO 4217 standard uppercase codes (`chk_currency`).
- Client requests containing prices (`price`, `totalPrice`, `amount`) are rejected immediately by client validation and cannot be inserted into the database.

---

## 7. Booking Lifecycle State Machine Controls

The database enforces valid lifecycle transitions across `BookingStatus`:
- Initial client request creates a `draft` record.
- Background inventory hold promotes record to `held`.
- Awaiting payment gate: `awaiting_payment`.
- Confirmed booking: `confirmed` (strictly authorized by server webhook upon payment settlement).
- Digital ticket delivery: `ticket_issued`.
- Terminal states: `expired`, `cancelled`, `payment_failed`, `failed`, `refunded`.

---

## 8. Inventory Consistency & Double-Booking Prevention

### 8.1 Database Invariants
The `departure_inventory` table enforces a strict non-negative capacity invariant:
```sql
constraint chk_inventory_capacity_bounds
    check ((allocated_capacity + held_capacity) <= total_capacity)
```
Any atomic allocation that would push `allocated_capacity + held_capacity > total_capacity` throws error `23514` (check violation) and aborts the transaction.

### 8.2 Atomic Transaction Strategy (Future Implementation Specification)
In Feature 05.3, the reservation mutation will execute as an atomic PostgreSQL function:
```sql
-- Conceptual specification for Feature 05.3 atomic hold
create or replace function hold_departure_inventory(
    p_departure_id varchar,
    p_passenger_count integer,
    p_user_id uuid,
    p_idempotency_key varchar
) returns uuid as $$
declare
    v_reservation_id uuid;
begin
    -- 1. Row-level lock on inventory record
    perform 1 from departure_inventory
    where departure_id = p_departure_id
    for update;

    -- 2. Conditionally update held capacity
    update departure_inventory
    set held_capacity = held_capacity + p_passenger_count,
        version = version + 1
    where departure_id = p_departure_id
      and (allocated_capacity + held_capacity + p_passenger_count) <= total_capacity;

    if not found then
        raise exception 'INVENTORY_UNAVAILABLE';
    end if;

    -- 3. Insert reservation record
    ...
end;
$$ language plpgsql security definer;
```

## 9. Idempotency Design

- Idempotency keys are scoped per user: `UNIQUE (user_id, idempotency_key)`.
- Replaying the same idempotency key by the same user returns the original reservation result.
- Submitting an existing idempotency key with a conflicting request payload throws an idempotency conflict.
- Attackers cannot probe or replay another user's idempotency key because queries are partitioned by `auth.uid() = user_id`.

---

## 10. Hold Expiration & Cancellation Boundaries

- Temporary inventory holds carry a strict `hold_expires_at` timestamp (typically 10–15 minutes).
- Expired holds are released by a background reaper process, returning capacity to the available pool.
- Payments received after hold expiration trigger automatic refund flows rather than reviving dead inventory.

---

## 11. Trusted Payment Integration & Webhook Verification (Feature 05.4 Roadmap)

- Payment Intents will be created server-side with pre-calculated minor-unit amounts.
- Webhook endpoints verify cryptographic HMAC signatures before updating any booking status to `confirmed`.
- Client checkout redirect callbacks are treated purely as informational UI hints.

---

## 12. Digital Ticket Issuance Authority (Feature 05.5 Roadmap)

- Tickets can only be created once booking status is `confirmed`.
- Every ticket payload contains an authoritative issuing authority signature and a verification reference hash.

---

## 13. Sensitive-Data Protection

- Payment card PANs, CVV/CVC tokens, and banking credentials are never accepted by generic booking inputs or persisted in database tables.
- All errors are sanitized before returning to mobile clients; database connection strings and service-role keys are excluded from mobile bundles.
